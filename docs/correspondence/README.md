# Correspondence

**Verbatim external messages that a doc in this repo relies on as evidence.**
Vendor support replies, host answers, anything where a claim in `docs/` rests
on "they told us so" and the reader is entitled to check the wording.

Added 2026-08-24, when the Nexcess reply settled two blocking questions and
existed only as a file in one person's iCloud folder.

## Why this exists

`docs/` is prose we wrote. `data/` is the inventory a person maintains.
`history/` is the append-only ledger. An email from a vendor is none of those:
nobody may edit it, its value is that it is exactly what they said, and it is
the source behind claims made elsewhere.

Without somewhere to put it, that evidence lives in an inbox or a personal
cloud folder. This repo has been bitten by that shape twice: the gitignored
`ci/github-actions/` mirror and the project-memory pointer to a file that does
not exist. Both times the copy that lost was the one nobody could look at.
A claim marked "VERIFIED by Nexcess support" is unreviewable if the reply is
not somewhere a reviewer can read it.

## Rules

1. **Verbatim below the rule. Never edit the message.** If it was wrong, the
   correction is a new file and a note in the citing doc, not a fix here.
   A file whose body has been tidied is no longer evidence.
2. **One file per message.** A thread is several files, not one growing file.
3. **Every file carries a provenance block** above a `---`, and the block says
   so. It records direction, date, thread ID, account, what it replies to,
   where it was captured from, and, the useful part, **what it settles and
   which doc records that.** The block is the only text we wrote.
4. **Cite it from the doc that uses it**, not the other way round. This
   directory is a reference, never the place a decision is explained.
5. **Read it for secrets before committing.** Support threads quote
   configuration and occasionally credentials. Check for tokens, keys,
   passwords and personal contact details. If a message cannot be committed
   clean, redact it, mark the redaction inline, and say why in the provenance
   block. Do not leave it out of the repo silently.

## Naming

```
<ISO date>-<vendor>-<in|out>-<subject>.md
```

ISO date so the directory sorts chronologically, and because this repo has
already been confused by a `08242026` filename. `in` and `out` because "what
did we actually ask them" is a real question and a thread reads wrong without
it.

Example: `2026-08-24-nexcess-in-ssh-and-api-challenge.md`

## What does NOT go here

- **Anything we can re-measure.** Probe output, scan results, HTTP headers.
  Those belong to the run that produced them: `reports/` while fresh, the
  ledger once ingested. Correspondence is here precisely because it cannot be
  re-generated by running something.
- **Our own analysis of a message.** That goes in the doc that cites it. This
  directory holds what they said; `docs/NEXCESS-SUPPORT.md` holds what it means
  and what we did about it.
- **Anything containing a live credential**, redacted or otherwise, that would
  be better off never having been written down. See rule 5.
- **Internal meeting transcripts.** Decided 2026-08-24 over the Pods
  post-action regroup, which `docs/VULN-INTEL-REVIEW.md` section 0 quotes
  heavily. Three reasons, and they are specific to transcripts rather than a
  general squeamishness about internal material.

  First, this directory exists for statements of fact from OUTSIDE parties,
  where the exact wording is the evidence and we cannot ask them again. A
  colleague's half-finished sentence is not that, and we can just ask them.

  Second, auto-transcription is unreliable. The Pods transcript renders
  "clevermethod" as "clutter method" and "Lactalis" three different ways.
  Committing it makes a lossy machine reading look like a record.

  Third, candid internal discussion names clients in a security-incident
  context and includes people criticising each other's decisions. That is
  healthy in a meeting and corrosive in a repository that is about to move to
  a company GitHub org.

  **So: quote what was decided, attribute it, and cite the transcript by its
  location.** The Pods one is `Post Action regroup.vtt` in the Cowork
  Automation Portfolio `meeting-records` folder.
